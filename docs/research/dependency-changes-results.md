# 依赖变动与下游解锁可见（票 #9）试跑

日期：2026-09-10。入口：`http://127.0.0.1:30142/waygoal`（`npm run dev`）。票据：[#9](https://github.com/s0ftnote/Waygoal/issues/9)，父 Spec [#1](https://github.com/s0ftnote/Waygoal/issues/1)，前置 [#7](https://github.com/s0ftnote/Waygoal/issues/7)。

## 结论

来源文件里的前置和依赖关系一变，画布上的受影响票据跟着变，四种情形分得清：**等待**（还有前提没满足）、**可以往下走**（前提都满足了）、**已解决**、**已取消**。只有来源明确写着 `resolved` 的前置才算满足；取消、这次读不到、指不到票据、同号有多份，一律不算，票据继续等，并说明这条依赖要在来源里核对。取消一张前置票据不等于把它解决掉，也不会因此放行下游——要放行，得在来源里把那条依赖本身改掉。前置重新打开、来源新增一条依赖，票据就回到等待。刚从等待变成可以往下走的票据轻轻点亮一次，说明的文字一直留着；同一次变化不会因为反复读取或宿主重启再点一遍。解锁只是状态变化：不完成下游、不启动会话、不关掉地图，也不动用户自己摆好的布局。整个过程不产生任何聊天消息。

## 实现摘要

- 依赖判断挪到了「画布正在显示的这张地图」上（`mergeTicketScan`，[lib/waygoal-tickets.ts](../../apps/web/lib/waygoal-tickets.ts)）。原来只在当次读到的票据之间判断，于是一个这次读不到的前置会被说成「这张地图里找不到」——那是两回事。现在读不到的前置也在地图上，它照样挡着下游，并且说的是「现在读不到它」。
- 每条依赖记下它为什么还挡着（`holding`）：`waiting`（还在做）、`cancelled`（来源把它取消了）、`missing`、`ambiguous`、`unreadable`。满足是唯一一个空值，来自来源写着 `resolved`。除了 `waiting`，其余每一种都是「读不出结论」，需要用户在来源里核对（`needsCheck`，[lib/waygoal-types.ts](../../apps/web/lib/waygoal-types.ts)）。
- 票据自己的状态是 `waiting` / `unblocked` / `resolved` / `cancelled`（`unblocked` 用词表里「解锁」的说法）。来源对这张票据自己的结论优先：写着 resolved 就是已解决，写着取消就是已取消，都不因为它还名着一条依赖而被画布推翻。取消的写法只认一小组词（`cancelled`、`canceled`、`dropped`、`wontfix`、`out of scope`、`已取消`、`取消`、`移出范围`），和「只读一种本地布局」是同一个态度：认得的照实说，认不得的按原样显示、按未解决对待。
- 票据自己的结论和它写着的依赖是两件事，卡片上就是两个标记：一张来源已经写成 resolved、却还名着一条没满足的依赖的票据，两个标记同时显示，而不是把后者藏起来。
- 点亮记在画布记录里（`ticketWaiting`，[lib/waygoal-store.ts](../../apps/web/lib/waygoal-store.ts)）：记的是每张票据上次被看到时是不是在等。第一次看到它不再等的那份快照带上 `justUnblocked`，同时把新状态写回记录，因此后面的每次读取、以及重启后的宿主，都不会再说一遍。第一次就见到它不在等，不算变化，不点亮。只因为这次读不到前置而进入等待的，不记进这份记录——否则下一次读成功就会被当成「前置刚刚被满足」而亮一下，可来源根本没变。
- 点亮是一次 CSS 动画加一个 `data-unblocked` 标记；说明文字（卡片上的「前提都满足了」、完整视图里的「前提都满足了，这张票可以往下走。」）来自状态本身，和动画无关。减少动态效果时画布已有的全局规则关掉动画，状态和文字照常显示，卡片全程可点。
- 没有新建图执行引擎：依赖仍然是 `Blocked by:` 里的编号在同一张地图内解析，汇合就是「每一条都满足才放行」。

## 实测发现

- 「这次读不到」原本被说成「这张地图里找不到」：依赖判断只在当次读到的票据之间做，一个刚被删掉的前置就成了「从来没有过的编号」。两件事对用户的意思完全不同——一个是关系写错了，一个是现在看不到。判断的范围得和画布显示的范围一致。
- 判断放到合并之后，读取器就不再产出依赖结果，缓存里也不再存它。顺带的好处是缓存只剩来源文件说过的话，比较「这次读到的和上次一样吗」时少了一批派生字段。
- 点亮的一次性存在服务端记录里，代价是「谁先读到谁看见」：同时开着两个画布时，先读到那一次的那个页面才会亮。换成客户端比较两次快照可以避开这一点，但那样人不在的时候发生的变化就再也不会被指出来。选了前者。
- 取消要不要算解决，是这张票里唯一一处不能靠读文件决定的事：文件只说了状态是 `cancelled`，没说依赖它的那张票现在该怎么办。所以画布不替用户决定，只把这条关系标出来请他在来源里改。
- 「读不到」会不会引出一次假的点亮：会。一次失败的扫描让票据进入等待，读回来就成了「刚刚解锁」，可来源什么都没变。所以只因为读不到而等待的，不记进「上次是不是在等」。
- 票 #7 的「文件不见了就保留上次读到的」和本票的「按画布显示的内容判断依赖」合起来有一个后果：删掉一份同号票据，那个编号仍然算有多份，依赖它的票据继续是「无法确定」。这是一致的——画布上确实还留着两张——但用户目前没有办法从画布上清掉一张读不到的卡片。
- 六项浏览器检查原本只写着 `true`，靠前一句 `waitFor` 抛错。已经改成断言看得见的东西（卡片上的类名、依赖行里的文字），不然读检查清单的人无从判断它到底验了什么。
